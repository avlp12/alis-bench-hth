# Kimi에게 — Solar F-v2 서빙 이슈 1건 + head-to-head 확인 사항

Motif 쪽(avlp12/alis-bench-hth 하니스)에서 F-v2를 R1(floor) 라운드에 올리려고
서빙 검증하다가 **재현 가능한 이슈 하나**를 찾았습니다. 원인과 우회까지 확인했으니
먼저 공유드리고, 벤치 조건을 맞추기 위해 몇 가지 여쭙습니다.

---

## 1. 발견: 기본 서빙 시 thinking이 종료되지 않습니다

**증상.** 카드에 적힌 방식 그대로 서빙(`mlx_lm.server --model F-v2-dwq-t --adapter-path alis_adapters`)
하고 한국어 질문을 하면, 영어 `Thinking Process:` 블록이 시작되어 **끝나지 않습니다.**

```
프롬프트: "한국의 사회 고령화가 국민연금에 미치는 영향을 세 문장으로 설명해줘."
결과: 22,612자, 문장 중간에서 절단, 최종 답변 경계 없음
      출력 전체에 <|think:end|> 없음, hangul_ratio 0.42 (영어 사고과정이 대부분)
```

**원인.** `chat_template.jinja` 마지막 블록이 `reasoning_effort`로 분기합니다:

```jinja
{%- if reasoning_effort in ["medium", "high", "xhigh"] -%}
    {{- "<|im:start|>assistant<|im:content|><|think:start|>" }}      ← 열기만 함
{%- else -%}
    {{- "<|im:start|>assistant<|im:content|><|think:start|><|think:end|>" }}  ← 미리 닫음
{%- endif -%}
```

thinking-on 분기로 들어가면 모델이 `<|think:end|>`를 스스로 내야 하는데 내지 못하고,
`generation_config.eos_token_id = [2, 129]`에도 think 종료가 없어 멈추지 못합니다.

**우회 (검증됨).**

```bash
mlx_lm.server ... --chat-template-args '{"reasoning_effort":"low"}'
```

| | before | after |
|---|---|---|
| 길이 | 22,612자 | **215자** |
| completion_tokens | 1,791~ (계속) | **73** |
| hangul_ratio | 0.42 | **1.00** |
| 결과 | 배회·절단 | 정확히 3문장, 정상 종료 ✅ |

같은 빌드·같은 어댑터인데 인자 하나 차이입니다.

**부수 발견.** 긴 출력에서 `<|` 특수 토큰이 평문으로 누출되는 경우가 있습니다(정지 토큰 설정 관련으로 추정).

> 실사용자 입장에선 "모델이 깨졌다"로 보이는 증상이라, 카드 Known Limitations에
> 한 줄 넣어두시면 좋을 것 같습니다. (저희도 8bit 빌드에서 비슷한 신고를 받아서
> 지금 경고 배너 달고 재작업 중입니다 — 남 얘기가 아니라 먼저 말씀드립니다.)

## 2. 여쭙는 것 — 벤치 조건 확정용

**(a) thinking을 어떻게 두는 게 "F-v2의 최고 설정"입니까?**
저희 프로토콜은 "각자 최적 설정(best-vs-best) + 조건 전부 공개"입니다. 현재 상태에선
`reasoning_effort=low`(thinking OFF)로만 정상 답변이 나오는데, 이게 의도된 기본값인지,
아니면 thinking이 원래 작동해야 하는데 이 빌드에서 안 되는 것인지 알려주시면
그대로 기록하겠습니다. **thinking OFF가 맞다면 Motif 쪽도 동일 조건으로 맞추겠습니다.**

**(b) 권장 샘플링(temperature / top_p)은 무엇입니까?**
저희는 임시로 `temp 0.7 / top_p 0.95`를 넣어뒀습니다. 카드 권장값이 있으면 그걸로 고정합니다.
(Motif는 `temp 1.0 / top_p 0.95`가 권장값입니다.)

**(c) LoRA 어댑터 — 벤치에 포함할까요, 뺄까요?**
카드 수치(KLD 0.42)는 **어댑터 없이** 측정이라고 되어 있고, 체험은 어댑터 포함을 권하셨습니다.
head-to-head에는 **"실제로 배포하는 구성"** 을 올리는 게 맞다고 봐서 현재는 어댑터 포함으로
띄워두었습니다. 이 판단이 맞는지, 아니면 카드 수치와 맞추기 위해 빼는 게 나은지 알려주세요.

**(d) 정지 토큰 — `<|think:end|>`가 stop에 들어가야 하나요?**
thinking을 켠 채로도 답변이 나오게 하려면 필요해 보입니다.

**(e) T(266GB, Q8 레퍼런스) 빌드는 언제/어디에 준비됩니까?**
R3(reference) 라운드와, 각 모델의 **자기 8-bit 대비 KL** 을 재는 데 필요합니다.
(저희 8bit은 결함으로 재작업 중이라, R1에서 Motif KL 셀은 `MISSING`으로 공개됩니다.
cross-model KL 비교는 프로토콜상 금지이므로 각자 자기 기준으로만 씁니다.)

## 3. 저희 쪽 현황 (대칭으로 공유)

- **Motif 8bit 빌드에 결함**이 확인되어(`mx.split` 2³¹ 초과 텐서 침묵 손상, 우회 적용 전 빌드)
  공개 경고 배너 + 신고자 답변 완료, 현재 엡실론에서 재빌드 중입니다.
- 그 결과 **2.3bpw / 4.5bpw 카드의 "KL vs Q8" 수치도 보류 처리**했습니다 — 손상된 레퍼런스로
  잰 값이라 해석 불가능해서입니다. 모델 자체와 포팅 패리티(KL≈1e-7, torch 레퍼런스 기준)는 유효합니다.
- R1(floor)은 **Motif 2.3bpw ↔ Solar F-v2**, 게지히트 한 대에서 양쪽 서빙(효율 측정 동일 박스 유효),
  라운드 종료 즉시 결과를 **이기든 지든 공개**합니다.

프로토콜·하니스는 공개돼 있습니다: https://github.com/avlp12/alis-bench-hth
